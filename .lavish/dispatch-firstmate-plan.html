Dispatch design review · July 31, 2026

A Firstmate-like Dispatch without token-burning crewmates

Yes, Dispatch can provide the same pleasant “one place to hand off work and come back to outcomes” experience. Firstmate itself was not the expensive part: Codex crewmates burned the tokens by repeatedly waking while long checks were still running. The design therefore keeps the conversational manager and moves waiting out of every model loop.

Selected direction: observability plus a thin event-driven manager.

Build the pleasant single-manager experience, while making dispatchd own long validation, lifecycle state, and wakeups. Instrumentation ships in the same design so we can prove the worker-side savings.

Root cause: the measured Codex runtime returned from shell waits after roughly 30 seconds. Long validation forced crewmates through repeated model turns, and each turn replayed accumulated context. Firstmate’s own event-driven supervision was not the burn source. Telling workers to “wait better” could not remove the tool boundary.
What Dispatch already has

Most of the control plane exists

Keep unchanged

  • SQLite task ledger and explicit state transitions
  • Worktree isolation and per-repo worker limits
  • Worker and reviewer roles with bounded rejection loops
  • Herdr’s event-driven agent wait path for unattended tasks
  • Deterministic merge and cleanup ownership in dispatchd

Add narrowly

  • An immutable attempt record for every worker and reviewer process
  • Native structured usage capture at the CLI process boundary
  • dt usage plus focused-task and daily summaries in the TUI
  • A thin manager session that consumes bounded task deltas
  • A daemon-owned long-job lane that wakes or resumes workers only when results exist
Target architecture

LLMs decide; the daemon waits

Conversational manager

One human-facing session. Reads bounded task deltas, files work, explains outcomes, asks for decisions.

  • Wakes on user input
  • Receives child transition notifications
  • Ends its turn when idle
→

dispatchd + SQLite

The authority for queueing, waiting, retry caps, review state, merge gates, and attempt accounting.

  • No model calls to monitor
  • No state hidden in chat
  • Restart-safe
→

Worker attempts + job runner

Claude or Codex processes emit structured events. A separate daemon process owns long checks and returns only completed results.

  • Usage recorded by task and role
  • Zero-token waits in dispatchd
  • Failures remain inspectable
Hard invariant: no agent may poll another agent or a long-running validation job.
The critical worker protocol

Codex never waits for a long command

There are two useful rungs. Ship the known validation path first because it covers the measured no-mistakes and test-suite burn. Add arbitrary deferred commands only after the Codex JSON spike proves reliable session identity and resume behavior.

MVP · known checks

Daemon-owned validation

  • The crewmate edits, runs short checks, commits, and exits.
  • dispatchd launches the repo’s configured validation command as an ordinary child process.
  • The daemon blocks on the process at zero model tokens and records duration, output tail, and exit status.
  • Pass advances to review. Failure starts one bounded repair attempt with the completed result.
Follow-up · any long job

Deferred command plus resume

  • The crewmate submits a command, receives a job id immediately, records a deferred state, and exits.
  • The daemon runs the command and waits without an LLM.
  • On completion, Dispatch resumes the same Codex thread with a bounded result summary.
  • The format spike must prove thread-id capture and codex exec resume before this path is accepted.
Operational escape hatch: until generic resume is proven, route tasks whose core work is supervising long external jobs to a runtime with a measured true long wait or background completion wake. This is routing, not the final architecture.

Record facts first; derive cost later

Ground truth

Provider, model, role, start/end, exit code, input, cached input, output, reasoning when exposed, turns, tool-output bytes.

Waste signals

Wait-only turns, repeated empty polls, rejected rounds, failed attempts, context growth, and time spent after the last code change.

Separate overlays

Estimated dollars and provider quota headroom are useful, but they are not the ledger. Subscription quotas and cache pricing are not comparable across providers.

Smallest implementation sequence

Instrument before adding autonomy

Event and resume spike

Run harmless fixtures through codex exec --json and Claude --output-format stream-json. Lock down usage fields, thread identity, and whether Codex can be resumed with a completed job result. No generalized adapter until the evidence is captured.

go / no-go

Attempt ledger and manager shell

Add one task_attempts table and dt usage [id] --json. In parallel, make the thin manager a first-class Dispatch session that receives task-transition notifications and queries bounded deltas.

selected scope

Daemon-owned validation

Move configured long checks out of crewmate turns. The worker commits and exits; the daemon waits for validation, then advances or creates one repair attempt with the finished result.

measured fix

General deferred jobs if needed

Add submit, wait, and resume only if real tasks still show costly non-validation waits. A wait-only breaker remains a backstop, not the main solution.

Decision recorded

Observability plus the thin manager

Design both as one experience; keep runtime authority in the daemon.

The first implementation slice proves structured usage and Codex resume behavior, creates the attempt ledger, and establishes the manager’s transition-notification contract. Daemon-owned validation is the first worker-side cost fix.

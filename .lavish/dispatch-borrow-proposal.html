2. Named delivery modes as an explicit per-repo config

from firstmateunblocked — pr.go has landed

Why: firstmate names its three merge paths explicitly — no-mistakes (full pipeline), direct-PR, local-only — as a per-project config value. Dispatch already has the equivalent behavior implicitly (ratchet/report gates, PR vs. local merge), but no single named knob a user sets once per repo. Mostly a config/naming tidy-up, not new logic.

Where it hooks in: ~/.dispatch/config.toml alongside the existing per-repo max_workers; consumed in internal/daemon/pr.go where merge/PR decisions already happen — that file's previous in-flight changes are now committed, so this is safe to scope against the current shape.

Effort: small.

3. Explicit agent-selection precedence

from firstmatesafe to start now

Why: firstmate's backend selection order — per-task flag → env → config file → auto-detect → default — is a clean, documented pattern. Dispatch has the pieces (DISPATCH_WORKER_AGENT env, RoleSpawner mixing claude/codex per role) but no per-task CLI override and no single documented precedence order.

Where it hooks in: cmd/dt/commands/add.go/capture.go (add a --agent flag), consumed wherever RoleSpawner currently resolves env vars.

Effort: small.

4. General periodic cleanup/audit pass — and this is already M6

from firstmate's wedge-alarmunblocked — unattended.go has landed

Reframed per feedback: not just stale unattended tasks — a general periodic pass across the fleet that surfaces anything wrong (stuck tasks, tangled worktrees, orphaned branches) without you having to notice it yourself. Explicitly cheap: a scan job, not a standing LLM loop — firstmate's fm-watch.sh proves this can be done as zero-token bash, and that's the model here too, not an "obnoxiously expensive" always-on agent.

This turns out to already be planned: dispatch-prd_2.md §15 names M6 — "PM cadence": dt review digest, orphan detection against GraphPilot, and its own open question #7 asks "Is GraphPilot orphan detection v1?" Firstmate's wedge-alarm is useful as a reference for the escalation-cadence shape (surface once, then back off unless it recurs). Resolved below: the open question about the cross-reference target is settled now — GraphPilot's Linear migration (see the GraphPilot section) means the target is Linear directly, not a gp_node, once that stack merges.

Where it hooks in: internal/daemon/unattended.go for the live/unattended half (that file's prior in-flight changes have landed); the cross-reference target is the open question above, not a new file.

Effort: medium — but scope it as M6, not as a separate firstmate-inspired feature.

5. External event-driven wake (webhook/CI/Slack) — re-scoped, narrower than before

from Agent Deck's "Watchers"safe to start now

Why, narrowed: Agent Deck's "Watchers" cover two different things — internal task-transition notification, and external-event wake. The internal half was believed shipped via b837 ("Add a thin event-driven Dispatch manager session," done) — but see the correction directly below, its wake mechanism doesn't actually fire in real deployment. What's left, regardless, is genuinely external: a GitHub-webhook-triggered wake (CI finished, review comment posted) to cut review-gate latency below the daemon's PollInterval tick.

Where it hooks in: internal/daemon/daemon.go's tick loop is stable now; a webhook receiver would need its own listener process/port, which is new infrastructure this repo doesn't have yet (no HTTP server anywhere in dispatchd today) — confirm that's wanted before starting, since it's a bigger footprint than the rest of this list.

Effort: large.

Correction, from investigating why the manager feels slower than firstmate: b837's wake mechanism doesn't fire across processes

bug, filed as 1463

Traced it end to end. internal/db/notes.go's Subscribe()/publish() pair is an in-process Go channel registry keyed by *DB pointer. dispatchd (the daemon, which drives real task transitions) and dt manager (which runs Manager.Run()) are separate OS processes, each with their own *DB from a separate db.Open() call — confirmed dispatchd never even imports internal/manager. So the daemon's publish() calls can never reach the manager process's Subscribe() channel. manager_test.go's tests all open one shared db.Open() per test and drive both sides through it, which is exactly the case that doesn't happen in real deployment — so the gap passed review invisibly.

This is a real answer, not a vibe, to "why does our thin layer struggle to feel as fast/parallel as firstmate": firstmate's watcher (fm-watch.sh) is a bash classifier that genuinely spans process/session boundaries (it reads real state files and pane status independent of which process is asking), so it reliably absorbs benign wakes and only spends a model turn on actionable ones. Dispatch's manager's equivalent wake path is in-memory-only and, as shipped, silently never fires from the daemon's real transitions — it currently only ever wakes on human input.

6. Fleet state as a scriptable JSON snapshot — task list done, fleet health is the remaining gap

from firstmatenarrowed — in progress (a3db)

Why: firstmate's fm-fleet-snapshot.sh --json gives a scriptable, deterministic view of the whole fleet — task list and daemon/worker liveness — for external tooling.

Status update: the task-list half is done: --json is a persistent root flag (cmd/dt/main.go), and dt list --json/dt show <id> --json (cmd/dt/commands/query.go) both already exist and are in real use. What firstmate's snapshot has that dispatch still doesn't: daemon/worker liveness — no heartbeat, no PID file, no DB row for "is dispatchd alive right now." That gap is exactly what a3db (open, active) is building: a daemon heartbeat via db.SetMeta plus TUI display of last-seen. Once that lands, the meta key it writes is trivially exposed under dt list --json/a small dt fleet --json too.

Where it hooks in: once a3db's heartbeat meta key exists, surface it via the JSON output path already in query.go — no new command needed.

Effort: small, and mostly done via a3db already — just needs the JSON surface added once that heartbeat key lands.

Watch, don't build yet

Worktree sparse-checkout / gitignored-file inheritance from Agent Deck

Agent Deck's .worktreeinclude mechanism copies specific gitignored files (.env, local config, cached deps) into a fresh worktree, plus setup/destroy hook scripts. Watch until you actually run into it — no confirmed case yet of a dispatch worktree breaking because it's missing an untracked local file. Revisit if/when that happens.

Broader agent-CLI backend support from Agent Deck

Agent Deck supports Claude, Gemini, OpenCode, Codex, Copilot, Crush, Cursor, Hermes, plus custom tools via config. Backburner — Codex and Claude are the only agents actually available/in use right now, so generalizing RoleSpawner into a config-driven multi-backend spawner has no near-term driver. Revisit only if a third agent CLI becomes something you'd actually run.

MCP Socket Pool (Agent Deck)

Agent Deck shares MCP server processes across sessions via Unix sockets, claiming an 85-90% memory reduction (self-reported, not independently verified). Only relevant once dispatch's workers actually spin up MCP servers with meaningful per-session overhead — no evidence that's a real cost today. Revisit if/when it becomes one.

Secondmate-style persistent domain agent (firstmate) partial analog now exists

Firstmate's secondmates — a persistent sub-supervisor with its own home, owning a whole slice of work (e.g. "issue triage") — is still a genuinely bigger architectural idea than anything else on this list. Since this doc was written, b837 shipped a single conversational Dispatch manager session (wakes on transitions, ends idle, no polling). That's a narrower thing than secondmates — one flat manager, not domain-sliced sub-supervisors with their own hierarchy — but it's real lived experience with the "persistent low-idle-cost supervisor" shape now, which should inform rather than replace that dedicated design conversation if/when it happens.

A second, smaller point of alignment

The PRD's own risk table (§16) already independently flags: "the one thing worth borrowing from firstmate's backend abstraction" — keeping a tmux implementation as an escape hatch behind the thin internal/mux interface, given herdr is pre-1.0 and API churn is likely. That's the same idea this proposal's earlier comparison report surfaced independently, which is a good sign the two analyses converge rather than diverge — no new item needed here, it's already tracked.

Explicitly not borrowing

  • Firstmate's LLM-judgment dispatch model (the first mate deciding routing/escalation itself, +yolo) — the opposite of dispatch's core bet that Go/SQLite should govern, not the LLM.
  • Agent Deck's no-merge-gate pattern — obviously don't remove dispatch's mandatory ratchet/report acceptance condition. That gate is dispatch's actual differentiator versus both other tools.

Follow-up report

Firstmate, in depth — and can it live alongside dispatch?

Full feature inventory of firstmate (read directly from upstream/main, kunchenguid/firstmate), the same for dispatch/dt for fair comparison, then Agent Deck added as a third option, and a verdict on whether combining any of these makes sense — or whether Agent Deck is just worth switching to outright.

Bottom line

Firstmate and dispatch are not a clean combine — both implement the same core loop (watch a fleet of worktree-isolated agents, decide when to act) on opposite sides of a governance split: firstmate lets the LLM self-govern, dispatch pushes governance into Go + SQLite and reserves the LLM for five tiny calls. Agent Deck is a different animal again: a tmux-based session manager with strong deterministic plumbing and a genuinely good cost-tracking dashboard, but zero merge/review gate — it never tries to be firstmate's or dispatch's supervisor at all. See the verdict.

Part 1 — Firstmate

What it is

Not a model, harness, skill, MCP server, or CLI — an "agent distro": a cloned git repo of AGENTS.md + skills + bin/ scripts. You launch whatever coding CLI you already use (claude, grok --trust, pi, codex, opencode) inside the clone, and that session becomes "the first mate." README.md

Session backends

tmux is the verified reference default. herdr, zellij, orca, and cmux are all explicitly labeled experimental, each with its own documented limits. Selection order: per-task --backend flag → FM_BACKEND env → config/backend file → runtime auto-detection → tmux default. Treehouse supplies worktrees for tmux/herdr/zellij/cmux; Orca owns worktree + terminal lifecycle itself.

docs/architecture.md, bin/fm-backend.sh, bin/backends/*.sh

Skills: lazy-loaded, not upfront

Only AGENTS.md itself (~532 lines, ~7,500 est. tokens) always loads. Internal skills (.agents/skills/) load only at named, precise triggers — per AGENTS.md §13: "load them only at their precise triggers." This is the direct mechanism keeping firstmate's baseline context bounded, similar in spirit to Pi's approach from the prior report.

AGENTS.md §13, .agents/skills/*/SKILL.md, config/startup-memory-budget

Deterministic vs. LLM turn

Genuinely substantial bash/Python layer with zero model calls: fm-watch.sh (1059 lines, wake classification), fm-guard.sh, fm-crew-state.sh, busy-state classifiers, fleet snapshot/view generators, PR-check polling, worktree-tangle detection, all backend adapters. But the first mate's own dispatch decisions, brief-writing, escalation phrasing, and every crewmate's actual coding work still require an LLM turn.

bin/fm-watch.sh, bin/fm-guard.sh, bin/fm-busy-lib.sh, bin/fm-classify-lib.sh, bin/fm-fleet-snapshot.sh

State & persistence

All gitignored, split into data/ (durable), state/ (volatile), config/ (local knobs). Backlog is plain Markdown (data/backlog.md), optionally driven by an external tasks-axi CLI. Per-task: state/<id>.meta (key=value), state/<id>.status (append-only wake log, not current-state truth). Designed "restart-proof" — disk records are authoritative over in-memory conversation state.

AGENTS.md §2, .tasks.toml, docs/configuration.md

Review/merge workflow & config surface

Three per-project delivery modes (data/projects.md): no-mistakes (full validated pipeline → PR), direct-PR (push + open PR, no gate), local-only (guarded fast-forward merge via fm-merge-local.sh, no PR). fm-pr-merge.sh is the only sanctioned merge path (never merges a red PR; requires captain approval unless a +yolo flag is set per project). fm-teardown.sh refuses to tear down a worktree with unlanded/dirty work. Dispatch-of-work rules (config/crew-dispatch.json) are natural-language, resolved by the LLM itself against live quota data — not by shell script.

AGENTS.md §7, docs/architecture.md, bin/fm-pr-merge.sh, bin/fm-teardown.sh

Gaps & rough edges the docs admit to
  • codex-app — distinct from the already-supported codex CLI — would run crewmates inside Codex Desktop's own visible chat threads instead of a terminal session. Blocked because Codex Desktop currently exposes those host tools only to its own UI, with no shell-callable bridge for firstmate's bash scripts to create/send/read/archive a thread. Explicitly "not a runtime backend yet" until Codex Desktop ships a stable CLI/JSON-RPC/MCP transport (docs/codex-app-backend.md)
  • herdr/zellij/orca/cmux all self-labeled experimental; orca/cmux refuse --secondmate launches outright (not yet designed)
  • OpenCode's busy-queue-Enter behavior is an unhandled, documented known gap on the herdr adapter
  • A whole "wedge alarm" escalation subsystem exists specifically because away-mode delivery can get stuck (docs/wedge-alarm.md) — implying it's a real, recurring failure mode
  • Zellij's agent-liveness probe for secondmate recovery is explicitly marked "unverified"

CLI entry points: no standalone firstmate binary — you launch your existing agent CLI inside the clone. Chat slash-commands: /afk, /ahoy, /bearings, /updatefirstmate, /stow (Codex uses $-prefix). Over 90 bin/fm-*.sh scripts, catalogued in docs/scripts.md.

State machine

Nine statuses under a SQLite CHECK constraint: open, active, blocked, done, live, unattended, parked, killed, proposed. Every transition is Go-enforced, not agent-judgment — agent-filed work always lands proposed and needs a human dt reopen before it can run at all.

internal/db/db.go (taskSchemaV2), tasks.go, tasks_v2.go

No captain process

Flatter than firstmate by design: there's no single agent doing ongoing supervision reasoning. Supervision is a Go daemon tick loop plus a prompt (agentctx/session.md) that tells a captured session to act as planner and file children via dt add — which land proposed, gated by a human either way.

internal/daemon/daemon.go, internal/agentctx/session.md

herdr — dispatch's own mux

A separate binary dispatch shells out to via a small Mux interface (EnsureWorkspace, CreateTab, StartAgent, WaitAgent, AgentStates). agent wait is a blocking, event-driven socket call — explicitly built to avoid polling, after "a prior system burned 62M tokens polling a TUI." The package comment calls it "pre-1.0… the swap point": designed to be replaceable.

internal/mux/herdr.go

LLM footprint: five calls, total

Worktree creation, merging, state transitions, reject caps, dependency resolution are all plain Go — zero model calls. Exactly five stateless, one-shot LLM sites exist anywhere in the machinery: label generation, dedup judge, TUI fuzzy-command, TUI brief, acceptance-report reviewer — each claude -p --model haiku, 30s timeout. Everything else costing tokens is the worker/reviewer agents actually doing the coding work itself, which is unavoidable.

internal/llm

Two distinct review gates

v1 (queue): a brand-new reviewer process each round must end with VERDICT: approve/reject; reject increments a persisted count, reopens with prior review notes, capped at 3 before blocking. v2 (unattended): gate is either ratchet (shell command, must exit 0, 10-min timeout) or report (inline reviewer judging only the written acceptance condition); rejection is fed back into the same live session via PromptAgent, preserving context rather than starting fresh. A documented, since-fixed bug (rejected tasks reaching done because branch validation was skipped) shows this gate is actively hardened, not just designed on paper.

prompts/reviewer.md, internal/daemon/unattended.go, docs/bugs/2026-03-26-review-gate-bypass.md

CLI surface — v2 capture: go, adopt, kill, park, resume, promote, relabel, tui. v1 ledger: add, edit, show, dep, undep, claim, release, done, block, reopen, note, ready, list, init. Plus batch for atomic multi-verb execution from stdin.

Part 3 — Agent Deck

"Agent Deck" is not one product — five distinct GitHub repos use the name. The one that actually fits this comparison is asheshgoplani/agent-deck (640★, 109 forks, 129 contributors, MIT). The rest: a hardware Stream Deck dashboard, an Electron/WSL workflow app, a monitoring-only dashboard, and a smaller macOS-native lookalike (a-streetcoder/agent-deck, 94★) built on "Pi CLI" doing the same worktree-per-session idea — noted where relevant, but the analysis below is about asheshgoplani/agent-deck.

What it is

A Go CLI + terminal UI (Bubble Tea) built on tmux and SQLite: "one TUI for Claude, Gemini, OpenCode, Codex, and more." Not a captain/crew orchestrator by design — its own FAQ calls it "tmux plus AI awareness." Solo-maintained by Ashesh Goplani, 8 months old, actively recruiting co-maintainers. Free, MIT, no hosted tier — you pay only your own agent-CLI costs.

github.com/asheshgoplani/agent-deck (README, gh api)

Broadest backend list of the three

Claude Code, Gemini CLI, OpenCode, Codex, GitHub Copilot, Crush, Cursor (terminal), Hermes Agent, plus arbitrary custom tools via config — wider than firstmate's five and dispatch's two. Git worktrees are first-class: sparse-checkout inheritance, .worktreeinclude for gitignored files, setup/destroy hook scripts.

Deterministic plumbing, real cost tracking

Worktree/sparse-checkout materialization and setup/teardown run as plain shell scripts (sh -e, 60s timeout), not LLM calls; status detection ("Running"/"Waiting"/"Idle"/"Error") is structured polling, not LLM interpretation. Ships a genuine Cost Tracking Dashboard: per-model pricing for 14 models, automatic collection via a Claude Code transcript hook, budget limits with warnings, CSV/JSON export — directly answers the "token cost is invisible" half of the original complaint about firstmate, though Gemini/Codex/MiniMax cost collection is self-marked "untested."

"Conductor": a looser supervisor

Optional persistent session that watches for sessions needing help, auto-responds when confident, escalates to you when it can't, with Telegram/Slack remote control and a "Watchers" system (webhook/GitHub/ntfy/Slack) that wakes it on external events. Architecturally similar to firstmate's captain, but looser — it's opt-in monitoring/escalation, not a task-dispatch or decomposition layer.

No merge/review gate at all

agent-deck worktree finish "session" merges the branch, removes the worktree, and deletes the session — a direct merge with no reviewer verdict, no pipeline gate, no acceptance condition. This is the one clear architectural gap versus both firstmate (project-mode gates) and dispatch (mandatory ratchet/report acceptance condition before unattended).

Known limitations (from its own public feedback thread & README disclosures)
  • A session-corruption bug (one session's output bleeding into another) drove at least one user to switch away, per the public Feedback Hub discussion (258 participants)
  • Session naming/creation UX complaints; CLI argument pass-through gaps to the underlying claude process; crashes on macOS suspend with no error logging
  • 347 releases in ~8 months is an unusually fast cadence — consistent with heavy AI-assisted dogfooding (a contributor account literally named claude has 22 contributions), but also a signal of churn/instability risk
  • The claimed "85-90% MCP memory reduction" from its socket-pooling feature is a self-reported vendor number, not independently verified
  • No confirmed HN/Reddit discussion thread found despite direct searching — a real evidence gap on how broad non-creator usage actually is, beyond GitHub's own stars/contributors

Part 5 — Can you combine them? Should you just switch to Agent Deck?

Where it's genuinely antithetical

Both tools claim the same authority: "decide when a worktree's work is actionable, and merge/report on it." Firstmate's fm-watch.sh loop and dispatch's daemon tick loop would both be watching the same git worktrees, each with its own idea of task truth (firstmate's data/<id> Markdown vs. dispatch's SQLite row) and its own merge path (fm-pr-merge.sh vs. dispatch's MergeBranch). Running both as co-equal supervisors over the same repo is a two-writers-one-truth problem, not a feature combination.

What transplants cleanly

  • Lazy skill/prompt loading. Dispatch's prompts (session.md, worker.md, reviewer.md) are currently always-loaded; firstmate's trigger-gated skill loading is a direct pattern to borrow if those prompts grow.
  • Backend abstraction as inspiration. internal/mux/herdr.go already calls itself "the swap point" — firstmate's precedence order (flag → env → config file → auto-detect → default) is a reasonable template if dispatch ever adds a second mux backend.
  • Named delivery modes. Firstmate's no-mistakes/direct-PR/local-only naming maps almost directly onto dispatch's own no-mistakes skill integration and could become an explicit per-repo config knob rather than an implicit one.

Recommendation

Don't run both as parallel supervisors on the same repo. Pick one system of record for task truth and merge authority — dispatch is the stronger fit for the exact complaint that started this thread, since it already keeps orchestration almost entirely out of the LLM (five tiny calls vs. firstmate's LLM-judgment-heavy first mate) and gates everything through a real state machine instead of chat-session memory. Treat firstmate as a source of specific implementation ideas (lazy loading, backend precedence, delivery-mode naming) to fold into dispatch, not as a co-running system.

Should you just switch to Agent Deck?

Agent Deck doesn't compete with dispatch or firstmate — it competes with herdr and tmux/session-backend plumbing, one layer down. It's not trying to be a supervisor at all: no merge gate, no reviewer verdict, no task ledger. What it does well is exactly the two things firstmate feels raw and opaque on: deterministic worktree/session handling, and actual visibility into token/dollar spend via its cost dashboard — something neither firstmate nor dispatch currently offers.

If you switch to Agent Deck "altogether" in place of firstmate, you gain: broader backend support, better cost visibility, and a lighter/less raw feel — but you lose firstmate's supervised-crew model entirely; you'd be back to manually watching sessions and merging worktrees yourself, just with a nicer TUI for it. In place of dispatch, it's a clear step backward on the one axis this whole comparison keeps landing on: dispatch's mandatory acceptance-condition gate (ratchet/report) is precisely the deterministic safety rail Agent Deck doesn't have.

The actually interesting move: Agent Deck's cost-tracking dashboard and its worktree/sparse-checkout handling are things dispatch's herdr doesn't do today and could borrow, same spirit as the firstmate borrows above — not a reason to add a fourth supervisor into the mix.

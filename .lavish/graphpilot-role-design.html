Design conversation

What should graph-pilot actually be?

Three systems now touch "planning and execution of work": Linear, dispatch, and graph-pilot. Before doing any more borrowing/design work on dispatch, worth resolving what graph-pilot's actual remaining job is — because the evidence suggests it doesn't have one yet.

The load-bearing fact: graph-pilot has never been used on a real project

Checked directly against your actual Obsidian vault (~/Library/Mobile Documents/.../vault/): zero files contain gp: true, there's no graphpilot.yaml at the vault root (required for gp to even locate it), and the only node-shaped content anywhere in the repo is synthetic test fixtures. Meanwhile your own daily note from two days ago (2026-07-29.md) reads: "mapped out the big next steps to make graph-pilot actually worth using" — and that same day's app-usage log shows 24 minutes in Linear, with daily notes full of real Linear issue IDs (RES-125, RES-126, RES-141) as the actual day-to-day task references. Linear is where planning happens today. Graph-pilot is source code, specs, and tests.

What graph-pilot was designed to be

Original intent (March 2026 PRD + integration spec)

An Obsidian-vault-based visual planning surface with "first-class dispatch to Claude Code for implementation." Cycle: gp design (Claude drafts planning nodes) → review in Obsidian's graph view → gp launch (single session on one node) or gp dispatch (fan out to parallel dispatch tasks) → gp complete cascades unblocks. Explicit non-goal: "Replacing GitHub Issues, Jira, or any external project management tool." The GP/dispatch design principle, verbatim: "GP is source of truth for planning; Dispatch is source of truth for execution. Neither system fully subsumes the other."

graphpilot-prd.md, docs/superpowers/specs/2026-03-24-gp-dispatch-integration-design.md

What's actually crept in since

A Bug node type, a dashboard "bug drawer" and report form (git log de62c2d), a live gp serve dashboard, Obsidian canvas export, and (July 29) an in-canvas terminal overlay. The bug-tracking pieces directly contradict the PRD's own non-goal — the code has been drifting toward "replace an issue tracker" while the docs still say it explicitly won't. This is the same territory Linear already occupies, and occupies today, with real usage.

Three ways to resolve this

Not mutually compatible — pick one direction rather than letting the current drift continue by default.

A. Graph-pilot becomes a pure interface — over Linear and dispatch

leans toward your framing

Drop the vault as an independent source of truth. Graph-pilot becomes a visualization/launch layer: pull issues from Linear (via its API) and tasks from dispatch's SQLite, render the dependency graph and canvas from that combined read, and keep gp launch/gp dispatch as the "start work on this Linear issue" action. No independent node content, no bug-tracking node type — that's Linear's job now, explicitly.

Answers your question directly: yes, it's just an interface for dispatch — and for Linear too. Not a third planning substrate.

Cost: real integration work (a Linear API client, a mapping from Linear issue ↔ graph node ↔ dispatch task), and gives up the graph-native dependency modeling Linear's flat issue model doesn't really have.

B. Graph-pilot stays an independent planning substrate — but narrows to what Linear can't do

keeps original intent, needs real scoping

Keep the vault as its own source of truth, but explicitly retreat from anything Linear-shaped: kill the Bug node type and dashboard bug-drawer, stop trying to be a tracker. Scope graph-pilot specifically to messy, pre-formal technical shape-of-work — the multi-node dependency graphs and architecture sketching that happen before something becomes a clean enough Linear issue to file. A scratchpad/whiteboard layer that occasionally exports a formalized chunk into Linear once it's real.

Cost: requires actually defining "what's too messy for Linear yet" as a real, honest boundary — the same kind of boundary that already blurred once (bug tracking) without anyone deciding it should.

C. Retire graph-pilot's planning ambitions; keep only the dispatch hook

cut losses

Given zero real usage after ~4 months and Linear already doing the job, stop investing in graph-pilot as a planning surface at all. Linear handles planning, dispatch handles execution (including its own emerging M6 "PM cadence" / orphan-detection). If the gp sync-child/gp dispatch hook idea is still valuable, it becomes a much smaller "Linear ↔ dispatch" integration instead of a whole separate vault-based app to maintain.

Cost: writes off the March design and the graph/dependency-visualization idea entirely — only right if graph-native dependency modeling turns out not to matter to you in practice.

My read, offered as a starting point, not a conclusion

The evidence points at (A) or (C) over (B): "most of that should happen in Linear" is your own framing, Linear is the tool with actual daily usage, and (B) requires holding a boundary that has already drifted once without anyone deciding it should. Between A and C: A preserves the one thing Linear structurally isn't good at (multi-node dependency/readiness graphs), if that's a real need; C is the more honest move if the graph-native visualization was more interesting in theory than in the 4 months of practice so far. Worth being honest with yourself about which one that is before committing engineering time either way.

Open questions to resolve before implementation

  • Has the graph-native dependency/readiness visualization (nodes, links, findReady) actually been missed in the last 4 months, or was Linear's flat issue+project model sufficient the whole time?
  • If (A): does Linear's API expose enough (custom fields, relations) to represent dependency graphs it doesn't natively model well, or does graph-pilot end up re-inventing that layer anyway just reading from Linear instead of its own vault?
  • If (B): who enforces the "no bug tracking, no Linear-shaped features" boundary going forward, given it already slipped once with no explicit decision behind it?
  • Regardless of A/B/C: does dispatch's own M6 "PM cadence" (orphan detection, dt review digest) still want a GraphPilot dependency to cross-reference against, or should it target Linear directly instead, given graph-pilot's real-world adoption question mark?

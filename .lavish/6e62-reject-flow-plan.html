When automated review keeps rejecting, what should actually happen?

Case study: task 6e62 ("In-canvas terminals: backend pty bridge"), currently blocked with reason "reviewer rejected the work." It went through 5 reviewer spawns. Reading the actual notes and session logs, only 2 of those were real content rejections - the other 3 outcomes were misclassified by a bug in daemon.go. Fixed and tested below; a related fragility in how the reject count survived restarts got cleaned up along the way.

What actually happened

  • round 1
    reject
    Shared tmux "current window" bug - real, worker fixed it.
  • round 2
    reject
    Per-connection view-counter collision - real, worker fixed it.
  • round 3
    approve, but…
    Reviewer verified everything, printed VERDICT: approve, and also left an informational dt note (a heads-up for task 1fd4). The daemon saw "reviewer left a note" and treated it as a rejection. reviewRound hits 3, task blocked.
  • round 4
    infra
    Human reopened. Reviewer session logged just "Execution error" - no verdict, no note. Blocked again via the separate crash/malformed-output path. Not evidence of the same bug - flagging it, not diagnosing it further here.
  • round 5
    approve, but…
    Human reopened again. Reviewer re-verified (no source changes needed), approved, left a note again - same misclassification. Currently blocked, again, on already-approved work.

Root cause

handleReviewerResult in internal/daemon/daemon.go checks "did the reviewer leave a new note" before it checks the actual verdict. That check used to be safe: the function it replaced was only ever called after a non-zero exit, where a note could only mean an intentional reject. Now it's called on every reviewer exit, approve included - and prompts/reviewer.md never told the reviewer it couldn't leave a note on approval, so it reasonably does (round 3's note carried a real, useful warning for 1fd4). Any note now short-circuits straight into the rejection path, no matter what the verdict says.

internal/daemon/daemon.go:791 - if newReviewerNote { fires before parseVerdict(handle.Output()) is ever consulted.

The fix

Decide approve/reject from the verdict first - a note never overrides an explicit VERDICT: approve. Reject is decided by the verdict content alone too (a compliant reject exits non-zero on purpose, so exit code can't gate that branch). Notes are still used - just as the reason text for a confirmed rejection, not as the signal that one happened. No recursion, no new state, same bounded reopen/rejectCap loop and same protocol-retry-then-block path for malformed/crash output.

Shipped, with two new tests in tests/review_gate_test.go: TestDaemonIntegration_ApprovalWithNoteIsNotARejection (reviewer prints VERDICT: approve, exits 0, and leaves a note → task goes done, not blocked - the exact case that shipped this bug) and TestDaemonIntegration_RejectCountPersistsAcrossRestart (a task seeded with 2 prior rejections blocks on its very next rejection under a brand-new daemon instance, instead of getting a fresh 3-strike budget). Two existing test fixtures (rejectingReviewSpawner, dtDoneRejectSpawner) were coupled to the old bug - they simulated "rejection" with a note but no VERDICT: reject line, which the fix no longer honors. Updated both to a compliant rejectHandle. Full suite green, go vet clean.

The persistence question - resolved

Correction after digging further: the reject-round counter did not flatly reset to zero on dt reopen. It's an in-memory map, but spawnReady re-derives it from disk on any cache miss via recoverReviewRound - a filepath.Glob(taskID+"-review-*.log") count of session log files. That's why 6e62 re-blocked after just one more misclassified note instead of needing three: the glob had already accumulated 5 files by the time of the last reopen. It sort of worked, by accident.

That's fragile on three counts: it depends on session log files never being pruned, the glob pattern *-review-* also matches *-review-protocol-* files (so a malformed-verdict retry silently counts as a "rejection round" too), and it only works when SessionDir happens to be configured. The DB already has a reject_count column and an IncrementRejectCount method, proven in production by the v2 unattended path - so the fix was a straight swap: delete the glob-recovery hack, read/write the same column v1 already had sitting unused in its own Task struct. Net deletion, not addition.

Dispatch operating guidance · based on affd and d15b logs

Make the task state trustworthy before spending model time

The largest avoidable cost was not answer length. It was workers entering an invalid or incomplete state, then spending many tool turns discovering that fact through edits and tests.

Recommended operating rule: preflight the worktree and dependencies, run one cheap proof first, and stop/reopen explicitly when the proof fails. Do not automatically retry a blocked task on the same state.

Highest-value changes

1

Preflight every worker

Before the first task-specific tool call, verify branch, commit, required dependency commits/files, clean status, and expected verification commands. If wrong, block immediately with the exact required baseline. This would have prevented d15b’s divergent-baseline attempt and affd’s missing-file attempt.

2

Add a cheap proof before broad implementation

Require one minimal failing or passing end-to-end example for the task’s hardest handoff before running broad tests. For affd, the typed new_item_ids handoff returned zero plans; that should have become the first focused proof instead of a long planner-debugging loop.

3

Make blocked mean stop

A blocked task should not be automatically retried unless its baseline, dependencies, or task description changed. Preserve the blocker and require an explicit reopen after the decision is made. This is the strongest protection against repeated cached-context spend.

4

Serialize edits to shared workflow files

Do not run workers that can modify the same workflow surface concurrently. affd explicitly encountered concurrent edits, which made safe verification impossible and increased retry pressure.

5

Use verification tiers

Run in order: syntax/lint, one focused example, targeted tractability or unit checks, then the full suite. Record which tier failed and stop when the failure is environmental or foundational. Do not spend a full Bazel run when the target is unavailable or the baseline is wrong.

Improve task authoring

Task descriptions should name the exact base/dependency commit, files expected to exist, the smallest acceptance example, verification tiers, and the conditions that require blocking. Keep the scope narrow enough that a worker can finish in one coherent pass; split only when multiple independent subsystems genuinely need separate ownership.

What not to build yet

Do not start with a large token-budget controller, custom planner, or orchestration policy engine. A small preflight plus explicit blocked-state retry rule addresses the observed waste. Add per-task budgets or automatic escalation only if logs show the simpler guard is insufficient.

Evidence: local Codex session logs for the 24-hour window. This is an operating proposal, not an implementation change.

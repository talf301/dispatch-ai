Design conversation, not a ticket

Secondmate-style persistent domain agents for dispatch

Spun out of dispatch-borrow-proposal.html's "watch, don't build yet" list. You named two concrete candidates, so this is scoped to those two rather than the abstract idea. Goal here: agree on shape before anyone writes code.

Current state

Dispatch has one flat manager today, and its wake is half-broken

dt manager (internal/manager/manager.go, task b837) is a single conversational session meant to wake on human input or actionable task transitions. Just found while investigating a related question: the transition-wake half doesn't actually fire in real deployment — dispatchd and dt manager are separate processes, and the event pub/sub is in-process-only, so the daemon's real transitions never reach the manager. Filed as 1463. Any secondmate design inherits this same wake-plumbing problem, so it's worth fixing once, underneath both.

Firstmate's actual secondmate shape

From ~/Documents/firstmate's bin/fm-secondmate-*.sh scripts: a secondmate is a separate persistent session with its own home/state directory, not a mode of the main captain session. When the first mate needs something from a domain a secondmate owns, it sends a marked request; the secondmate reports back on a shared status channel using a correlation token (corr=<id>) so the reply routes to the right waiting request. There's a dedicated liveness check (fm-secondmate-liveness.test.sh) — the architecture explicitly treats "is this secondmate actually alive" as something that needs checking, not assuming.

The load-bearing constraint this design must not violate

Dispatch's own operating rule (stated in this repo's CLAUDE.md-equivalent guidance, and enforced on every agent working in it): tasks start proposed and a human approves every reopen; no agent claims, completes, kills, or promotes tasks itself. This repo's "explicitly not borrowing" list already rejects firstmate's LLM-judgment dispatch model for exactly this reason — dispatch's bet is that Go/SQLite governs, not the LLM. Any secondmate that "unblocks things" has to work within that gate, not around it.

Candidate 1: PR-review digest secondmate

Your framing: keeps up with PRs you're tagged in as reviewer, has a breakdown ready for you.

Proposed shape

Cheap and periodic by default, not a standing LLM loop: poll gh search prs --review-requested=@me (or the equivalent GraphQL query) across whatever repos you care about, on a plain timer — no model turn spent just checking. Maintain a small durable digest (new table, or a file, following whatever the project's lightest existing pattern is) of what's open, how long it's been waiting, and any signal worth flagging (CI red, merge conflicts, a re-request after changes). Only spend a model turn to write the summary language when something in the digest actually changed since last time you looked, and only escalate to you (push into the manager, once its wake is fixed) for PRs that look time-sensitive or blocking someone.

Open question: does "ready for me" mean pull-on-demand (you ask the manager "what needs my review?" and it answers from the maintained digest) or push (it proactively surfaces new/aging PRs)? Both are cheap once the digest exists; picking one changes whether escalation cadence matters here at all.

Candidate 2: dispatch-unblocker secondmate

Your framing: handles menial dispatch stuff, escalates only if something's actually important or difficult.

This is the one that needs a real decision, not just a design

"Unblocking menial dispatch stuff" is doing a lot of work in that sentence. If it means reopening proposed tasks, approving merges, or resolving blocks itself, that's exactly the LLM-judgment-governs-lifecycle model this repo's own borrow-proposal already rejected, and it overrides the "human approves every reopen" rule that's currently enforced project-wide (including on me, right now, in this session). Worth being explicit about which of these you actually mean before any design gets written:

Option A — recommends, never acts

The secondmate watches the board (stuck tasks aging past a threshold, blocked tasks with a clear obvious next step, PRs sitting approved-and-unmerged — exactly the kind of thing this session just found with the graph-pilot stack), and surfaces a queued recommendation through the manager: "task X has been blocked for 3 days on Y, want me to reopen it?" You approve with a word; it never acts unilaterally. Zero change to the human-approves-every-reopen invariant.

Option B — acts, but only inside a pre-approved allowlist of non-lifecycle actions

A narrow, explicit list of mechanical actions that never touch task status: re-running a failed CI check, nudging a genuinely stalled worker (the kind of thing a3db's liveness work would make detectable), re-triggering a stuck merge check. Task lifecycle (reopen/promote/kill) stays human-only; only true busywork gets automated, and the allowlist is small enough to audit at a glance.

Option C — real autonomy over lifecycle decisions

If this is actually what you want, it's a deliberate policy change to dispatch's core invariant, not a secondmate feature — needs its own explicit decision (and probably its own scoped trust boundary: which tasks, which repos, what "menial" means precisely) before any code gets written. Flagging it as a distinct option rather than assuming it's what "unblocking" means.

One architecture question that applies to both candidates

Firstmate's secondmates are separate persistent sessions with their own home/state — not a mode of the main captain. Does a dispatch secondmate need that same separation (its own herdr pane/session, its own durable state), or is it closer to a scheduled job that occasionally writes into the existing manager's conversation? The PR-digest candidate leans toward "mostly a cheap background job with occasional manager-surfaced output" — it doesn't obviously need a persistent conversational identity of its own. The unblocker candidate (especially Option A/B) is similar. If neither candidate actually needs "its own home," that's worth knowing before building toward firstmate's heavier pattern by default.

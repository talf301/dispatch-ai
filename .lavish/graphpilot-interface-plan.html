Implementation plan — direction A

Graph-pilot as a pure interface over Linear + dispatch

Goal: graph-pilot stops being an independent planning source of truth and becomes a visualization/launch layer over Linear (planning) and dispatch (execution). No independent node content, no bug-tracking. Phased so the safest, most-grounded change lands first.

Current state (verified against the actual code)

gp launch today

graphpilot/src/cli.ts:cmdLaunch resolves the node's project root, assembles context from linked nodes, then spawn("claude", ["--dangerously-skip-permissions", prompt], { cwd: projectRoot }) directly — in the real checkout, no worktree, no dispatch involvement, no board visibility.

gp dispatch today — already close to "pure interface"

graphpilot/src/dispatch.ts:gpDispatch already shells out to the real dt CLI (dtExec → execFileSync("dt", [...]), e.g. dt show <id> --json) and just mirrors the resulting task tree into vault nodes + regenerates the canvas for visualization. It does not duplicate dispatch's execution logic today.

Confirmed while researching this plan: dispatch's CLI already has a working --json global flag (cmd/dt/commands/output.go, used by dt show/dt list via query.go) — the earlier borrow-proposal's "fleet JSON snapshot" item may be partially redundant with what already exists; worth checking scope overlap before building that item.

Phase 1 — gp launch shells out to dt go

Lowest-risk, most-grounded change. Do this first and validate it before touching anything Linear-related.

What changes

Replace cmdLaunch's direct spawn("claude", ...) with a call to dt go "<assembled context>" --repo <projectRoot> --json (via execFileSync, same pattern gpDispatch already uses for dtExec). Parse the returned task JSON (cmd/dt/commands/capture.go:NewGoCmd already supports --repo and --json, confirmed by reading it directly) and write task.id/task.workdir into the GP node's frontmatter (session: field, mirroring how gpDispatch already tracks dispatch-task-id).

What this gains: worktree isolation (currently zero for gp launch), board visibility (dt list/TUI now show launched-from-graph work), and removes a second bespoke "spawn claude" code path — graph-pilot no longer needs its own tmux/session logic for this case at all, since dt go already does herdr pane creation, focus, and prompt delivery.

Real architectural gap this introduces — flagged, not solved here

This breaks typing into a claude session from the in-canvas terminal overlay. Today, gp launch's tmux window (spawned by spawnWindow(node.meta.id, ...) in serve.ts) directly contains the interactive claude process (stdio: "inherit") — that's exactly what the July 29 terminal overlay (tmux.ts, windowForNode) attaches to and lets you type into. dt go runs the actual claude process inside a herdr pane instead — a different terminal multiplexer than graphpilot's own "graphpilot" tmux session. dt go itself returns immediately after printing the task summary; there is currently no bridge from graphpilot's tmux-based terminal viewer to a herdr pane. Routing gp launch through dt go as scoped would leave the in-canvas terminal with nothing live to show for that node. Not resolving this now — noting it as an open cost, see the "keep it in one repo?" question below.
Resolved, not a risk: permission-prompt behavior change is moot — with auto mode, no interactive claude session needs --dangerously-skip-permissions anymore. Dropped as a concern.
Confirmed need, not just a maybe: assembleContext (graphpilot/src/context.ts) pulls in content from multiple linked nodes and this will need to launch with that context. dt go currently only takes the thought as a single positional CLI argument — add a way to pass a larger context blob (e.g. --thought-file, or read from stdin) as part of this same pass, not as a follow-on.

Phase 2 — drop Linear-shaped features, keep gp dispatch mostly as-is

Per feedback: do this together with Phase 1 in one pass, no gate in between — real usage is low right now, no need for careful staged validation.

What changes

Remove the Bug node type and the dashboard bug-drawer/report form (git log de62c2d) — that's Linear's job, and keeping it is exactly the scope-creep the design conversation flagged. gp dispatch itself needs little to no change: it already treats dt as the execution source of truth and only mirrors state for visualization, which is the correct shape for a pure interface.

Smaller follow-on: since gp dispatch already depends on dt show --json, and the borrow-proposal separately considered a dt fleet --json/dt list --json whole-tree snapshot, check whether that item should be re-scoped as "extend the JSON support graph-pilot already depends on" rather than a firstmate-inspired addition from scratch.

Resolved: stay two repos, graph-pilot depends on dispatch directly

Decision

Keep graph-pilot and dispatch as separate repos. Graph-pilot imports dispatch directly as a dependency rather than only shelling out via the dt CLI. Explicitly acknowledged: the tmux (graph-pilot) vs. herdr (dispatch) mux split still needs unifying — that's real follow-on work, not resolved by this plan, and is the concrete fix for the terminal-view gap flagged above (graph-pilot's viewer needs to speak herdr, or the two need one shared mux).

Phase 3 — Linear as the planning source of truth (bigger, less specified, separate pass)

The shape

Graph-pilot's canvas/graph view renders from Linear issues (pulled via Linear's API, not the vault frontmatter) plus dispatch tasks (already working, via dt show --json). Dependencies come from Linear's own issue relations rather than graph-pilot's depends-on/blocks frontmatter fields.

Deliberately under-specified — needs its own design pass, not assumptions baked in here:
  • Does Linear's API/relations model represent dependency graphs richly enough, or does graph-pilot end up re-deriving a graph structure Linear doesn't natively expose well?
  • Read-only mirror of Linear, or does graph-pilot need write access (creating/updating Linear issues from the canvas)? Different auth/scope requirements.
  • Does the vault go away entirely, or does it become a thin local cache for offline canvas rendering (refreshed on gp sync)?
  • Rate limits / caching strategy for a live Linear API dependency, given gp serve's dashboard currently assumes fast local file reads.

Sequencing

  • Phase 1+2 together: gp launch → dt go, drop bug-tracking
  • Decide: merge into dispatch, or stay two repos?
  • Phase 3: Linear integration (separate design pass)

Per feedback, phases 1 and 2 run together as one low-ceremony pass — no staged validation gate, since real usage is low right now. Phase 3 (Linear) stays a separate, later design pass regardless; it's the only piece that's genuinely bigger than "not being particularly careful" should apply to.

Grounded directly against graphpilot/src/cli.ts, graphpilot/src/dispatch.ts, and dispatch-ai's cmd/dt/commands/capture.go and output.go/query.go — not assumed from the earlier design conversation alone.
